# 纯视觉实时人物画框系统开发文档

版本：v1.0  
日期：2026-09-20  
目标硬件：AMD Ryzen 7 9700X + NVIDIA GeForce RTX 5070  
目标场景：本地部署纯视觉模型，对当前电脑画面中正在播放的电视剧人物进行实时画框  
核心约束：允许联网；不保存截图；不记录视频；不做人脸身份识别；不读取字幕、音频、网页 DOM、播放器元数据；不导入外部视频/图片数据

---

## 1. 项目定位

本项目是一套本地实时视觉检测系统。系统只处理当前屏幕上可见的像素帧，通过本地部署的视觉模型检测画面中的人物，并用透明悬浮层在屏幕上绘制人物边框。

它不是视频分析平台，不是人脸识别系统，不是内容爬取系统，不是播放器插件，也不是截图/录屏工具。

一句话定义：

> 系统只在内存中读取当前屏幕像素，使用本地视觉模型检测 `person`，实时显示边框，不保存、不上传、不识别身份。

---

## 2. 需求边界

### 2.1 必须实现

1. 本地部署视觉模型。
2. 对当前电脑屏幕中正在播放的电视剧画面进行人物检测。
3. 在人物位置绘制矩形框。
4. 支持实时运行，目标达到肉眼流畅。
5. 允许联网，但网络不得传输画面、截图、视频帧、人物框轨迹、身份信息。
6. 不保存截图。
7. 不记录视频。
8. 不导入任何外部视频、图片、字幕、音频或历史数据。
9. 不做人脸身份识别。
10. 不读取字幕、音频、网页 DOM、播放器标题、视频文件路径、播放平台账号信息。

### 2.2 明确不做

1. 不识别演员姓名。
2. 不做人脸比对。
3. 不做跨剧集人物追踪。
4. 不保存检测历史。
5. 不生成截图报告。
6. 不上传画面给云端模型。
7. 不调用云端视觉 API。
8. 不绕过 DRM 或受保护内容机制。
9. 不读取浏览器页面结构、字幕文本、弹幕、音频或系统剪贴板。
10. 不做基于剧情、台词、视频源信息的推断。

### 2.3 关于“不读取”的准确解释

如果系统要在屏幕上画框，必须读取当前屏幕像素帧，否则无法知道人物位置。因此这里的“不读取、不导入任何数据”应解释为：

1. 不读取外部数据源。
2. 不导入本地视频、图片、字幕、数据库。
3. 不读取播放器元数据。
4. 不读取网页 DOM。
5. 不读取音频流。
6. 不读取用户文件。
7. 只读取当前屏幕上的瞬时像素帧，并且只保留在内存中。
8. 帧处理完成后立即释放或覆盖，不落盘、不缓存成文件。

比赛答辩时可以这样表述：

> 本系统的数据平面只包含当前屏幕像素帧，且像素帧仅存在于内存中的短生命周期缓冲区。系统不保存、不上传、不导入、不复用任何画面数据。

## 3. 总体架构

### 3.1 高层数据流

```text
当前屏幕画面
  -> 屏幕采集模块
  -> 内存帧缓冲
  -> 图像预处理
  -> 本地人物检测模型
  -> 后处理 NMS
  -> 多目标跟踪/稳框
  -> 坐标映射
  -> 透明悬浮窗绘制边框
```

### 3.2 控制流与数据流分离

系统应分为两个平面：

```text
数据平面：
屏幕像素帧 -> 本地推理 -> 边框结果 -> 本地绘制

控制平面：
联网状态 -> 比赛心跳/授权/版本检查/非画面型指标上报
```

关键原则：

1. 数据平面不联网。
2. 控制平面不能接触截图、视频帧、像素数组。
3. 网络模块只允许发送非内容信息，例如程序版本、GPU 型号、FPS 数值、运行状态码。
4. 如果比赛规则连 FPS 都不允许存储或上传，则控制平面只做在线鉴权或心跳，不发送性能指标。

## 4. 推荐技术路线

### 4.1 推荐路线：Python MVP + TensorRT 竞赛版

建议分两阶段开发。

第一阶段做 MVP：

```text
Python
  + 屏幕采集
  + YOLO/RT-DETR 人物检测
  + OpenCV 后处理
  + 透明窗口画框
```

第二阶段做比赛版：

```text
C++ 或 Python 高性能版
  + DXGI Desktop Duplication
  + ONNX/TensorRT 推理
  + ByteTrack/OC-SORT 稳框
  + Direct2D/Qt/ImGui 透明覆盖层
  + 网络隔离与隐私审计
```

### 4.2 推荐模型

优先使用目标检测模型，而不是人脸模型。

推荐候选：

1. YOLO 系列检测模型：适合实时人物检测，工程成熟，容易导出 ONNX/TensorRT。
2. RT-DETR 系列：检测质量较好，推理链路相对复杂。
3. YOLO-Pose：如果比赛需要“人物骨架/姿态”，可以用；如果只是画框，不必使用。

建议初版使用：

```text
类别：person
输入尺寸：640 或 960
精度：FP16
batch：1
置信度阈值：0.25 - 0.45
NMS IoU：0.45 - 0.7
```

模型选择建议：

| 目标 | 推荐 |
|---|---|
| 最快完成 MVP | YOLO 小模型 |
| 稳定实时画框 | YOLO small/medium |
| 更高精度 | RT-DETR 或更大 YOLO |
| 更低延迟 | TensorRT FP16 engine |
| 更稳画框 | 检测模型 + ByteTrack |

### 4.3 推荐推理后端

优先级：

1. TensorRT Engine：比赛演示性能最好。
2. ONNX Runtime + TensorRT Execution Provider：部署灵活，调试方便。
3. ONNX Runtime + CUDA Execution Provider：兼容性较好，性能略低于 TensorRT。
4. PyTorch：适合调试，不建议作为最终比赛运行后端。

## 6. 模块设计

### 6.1 屏幕采集模块

职责：

1. 获取当前屏幕帧。
2. 支持选择显示器或窗口区域。
3. 将帧放入内存队列。
4. 不保存帧。
5. 不暴露帧给网络模块。

Windows 推荐：

```text
DXGI Desktop Duplication API
```

原因：

1. 低延迟。
2. 适合实时桌面捕获。
3. 能获取桌面内容和脏矩形元数据。
4. 比普通截图 API 更适合高帧率处理。

注意：

1. 如果视频平台使用受保护内容，采集结果可能是黑屏。
2. 系统不应绕过 DRM 或保护机制。
3. 比赛素材应使用允许本地显示捕获的播放源。

备选：

```text
MSS / DXcam / Windows Graphics Capture / OBS 虚拟源
```

不建议初期就依赖 OBS 插件，除非比赛允许且评审环境已安装。

### 6.2 帧缓冲模块

职责：

1. 维护短生命周期帧队列。
2. 队列长度建议为 1 到 3。
3. 推理慢时丢弃旧帧，只处理最新帧。
4. 避免延迟积压。

推荐策略：

```text
capture_thread:
  不断抓取最新屏幕帧
  如果队列满，丢弃旧帧

infer_thread:
  只取最新帧推理
```

内存约束：

1. 不写入磁盘。
2. 不创建临时图片文件。
3. 不使用系统剪贴板。
4. 不保留超过必要生命周期的帧。

### 6.3 图像预处理模块

职责：

1. RGBA/BGRA 转 RGB。
2. resize/letterbox。
3. 归一化。
4. HWC 转 CHW。
5. CPU/GPU 内存拷贝控制。

建议：

1. MVP 阶段可用 OpenCV/Numpy。
2. 比赛版尽量减少 CPU-GPU 往返。
3. 输入分辨率固定可简化 TensorRT engine。
4. 如果电视剧画面在播放器窗口内，可以只截播放器区域，减少无效画面。

### 6.4 人物检测模块

职责：

1. 加载本地模型。
2. 对当前帧执行推理。
3. 输出人物候选框。
4. 只保留 `person` 类别。

输出结构建议：

```text
Detection {
  float x1;
  float y1;
  float x2;
  float y2;
  float confidence;
  int class_id;       // person
}
```

安全边界：

1. 不输出人脸特征。
2. 不输出身份 embedding。
3. 不保存检测结果历史。
4. 不上传检测结果。

### 6.5 后处理模块

职责：

1. 置信度过滤。
2. NMS 去重。
3. 坐标还原到屏幕坐标。
4. 过滤异常框。

建议参数：

```text
confidence_threshold = 0.30
nms_iou_threshold = 0.55
min_box_area = 20 * 40
max_box_area = screen_area * 0.95
```

电视剧人物场景常见问题：

1. 半身、侧脸、背影仍应算人物。
2. 远景人群可能密集，NMS 阈值不能太低。
3. 镜头切换时框会跳变，需要跟踪模块平滑。
4. 暗光场景可能漏检，需要调低阈值或换更强模型。

### 6.6 多目标跟踪/稳框模块

职责：

1. 让框稳定。
2. 减少闪烁。
3. 给短时间漏检做平滑补偿。
4. 镜头切换时快速清空旧轨迹。

推荐算法：

```text
SORT
ByteTrack
OC-SORT
```

比赛版建议使用 ByteTrack，因为它适合目标检测框跟踪，工程成熟。

隐私边界：

1. 跟踪 ID 只存在于内存。
2. 跟踪 ID 不表示真实身份。
3. 不跨程序运行保留。
4. 不写入文件。
5. 不上传。

### 6.7 透明悬浮窗绘制模块

职责：

1. 创建置顶透明窗口。
2. 对检测到的人物绘制矩形框。
3. 不影响用户操作播放器。
4. 支持多显示器和 DPI 缩放。

Windows 推荐实现：

```text
Win32 layered window
Direct2D / Direct3D / ImGui / Qt
```

关键要求：

1. 窗口置顶。
2. 背景透明。
3. 鼠标穿透。
4. 边框颜色醒目。
5. 绘制延迟低。
6. 不截获键盘鼠标。

UI 建议：

1. 只画框，不显示姓名。
2. 可显示 `person` 或置信度，但比赛隐私要求严格时只画框。
3. 可显示 FPS/延迟，但不要显示视频标题、文件路径、用户信息。
4. 提供快捷键开关画框。

### 6.8 网络模块

比赛要求联网，但本系统必须保证网络模块不接触画面数据。

允许的网络用途：

1. 比赛平台在线鉴权。
2. 心跳。
3. 版本检查。
4. 下载比赛规定的模型文件或规则文件，如果比赛允许。
5. 上报非内容型运行状态，例如 `online=true`。

不允许的网络内容：

1. 截图。
2. 视频帧。
3. base64 图片。
4. 视频片段。
5. 音频片段。
6. OCR 文本。
7. 字幕。
8. 人脸特征。
9. 人物轨迹。
10. 播放器标题。
11. 当前 URL。
12. 文件路径。
13. 用户账号信息。

推荐网络 Payload：

```json
{
  "client_version": "1.0.0",
  "runtime": "local",
  "gpu": "RTX 5070",
  "status": "running",
  "privacy_mode": "zero_retention"
}
```

如果比赛要求上报性能：

```json
{
  "fps": 31.2,
  "latency_ms": 38.5,
  "gpu_utilization_percent": 42,
  "privacy_mode": "zero_retention"
}
```

注意：严格模式下，连检测人数、框坐标、轨迹 ID 都不要上报，因为这些虽然不是截图，但仍可能反映画面内容。

### 6.9 隐私保护模块

建议实现一个 `PrivacyGuard`，用工程手段约束“零留存”。

职责：

1. 禁止截图保存。
2. 禁止视频写入。
3. 禁止帧数据进入网络模块。
4. 禁止日志记录图片路径、URL、窗口标题、字幕文本。
5. 检测运行时是否创建了可疑文件。
6. 提供比赛展示用隐私状态面板。

隐私状态面板可显示：

```text
Screen frames saved: 0
Video files recorded: 0
Cloud vision calls: disabled
Face recognition: disabled
OCR: disabled
Audio input: disabled
Network mode: control-plane only
```

## 7. 进程与线程模型

推荐线程结构：

```text
Main Thread
  -> 初始化配置
  -> 启动窗口
  -> 启动各工作线程

Capture Thread
  -> 屏幕采集
  -> 写入最新帧队列

Inference Thread
  -> 读取最新帧
  -> 预处理
  -> 模型推理
  -> 后处理
  -> 写入检测结果队列

Tracking Thread 或 Inference Thread 内联
  -> 稳框
  -> 输出屏幕坐标

Overlay/UI Thread
  -> 读取最新边框
  -> 绘制透明覆盖层

Network Thread
  -> 心跳/鉴权
  -> 禁止访问帧队列
```

建议用两个队列：

```text
FrameQueue: 只在 Capture -> Inference 之间使用
BoxQueue: 只在 Inference/Tracking -> Overlay 之间使用
```

不要让网络线程拿到 `FrameQueue` 或原始图像对象引用。

## 8. 坐标系统设计

屏幕画框最容易出问题的是坐标映射。

需要处理：

1. 模型输入坐标。
2. letterbox 缩放坐标。
3. 捕获区域坐标。
4. 显示器坐标。
5. Windows DPI 缩放。
6. 多显示器偏移。
7. 播放器窗口移动。

推荐内部统一结构：

```text
FrameRegion {
  int screen_x;
  int screen_y;
  int width;
  int height;
  float dpi_scale;
  int monitor_id;
}
```

模型输出还原公式：

```text
model_box
  -> 去除 letterbox padding
  -> 除以 resize scale
  -> 加上 capture_region 左上角偏移
  -> 乘/除 DPI 缩放修正
  -> 得到屏幕坐标 box
```

验收方式：

1. 播放器窗口拖动后，框仍贴住人物。
2. 切换全屏后，框仍贴住人物。
3. 多显示器播放时，框不偏移。
4. Windows 缩放 125%/150% 时，框不偏移。

## 9. 零留存策略

### 9.1 代码层禁止项

项目中应禁止或审计以下调用：

```text
cv2.imwrite
cv2.VideoWriter
PIL.Image.save
imageio.imwrite
imageio.mimsave
ffmpeg output
open(..., "wb") 写图片/视频
requests.post 上传图片/bytes
websocket 发送图片 bytes/base64
```

如果确实需要下载模型文件，模型文件下载路径必须固定到 `models/`，并且网络模块不能复用图片上传函数。

### 9.2 文件系统策略

运行目录建议：

```text
app/
  models/
    detector.engine
  config/
    runtime.yaml
  logs/
    app.log          // 可选；严格模式下禁用落盘日志
  cache/
    tensorrt/        // 只存 TensorRT engine/timing cache；不存画面
```

严格模式：

```text
logs: disabled
frame_cache: disabled
screenshot_output: disabled
video_output: disabled
network_content_upload: disabled
```

### 9.3 日志策略

推荐日志只包含：

1. 启动/停止。
2. 模型加载成功/失败。
3. FPS。
4. 延迟。
5. GPU 是否可用。
6. 网络心跳状态。
7. 隐私模式状态。

禁止日志包含：

1. 窗口标题。
2. URL。
3. 视频名称。
4. 文件路径。
5. 截图路径。
6. 检测框坐标历史。
7. 人物数量历史。
8. 任何 OCR 文本。

### 9.4 网络隔离策略

建议做两个工程约束：

1. `vision_core` 模块不依赖网络库。
2. `network_client` 模块不依赖图像类型。

例如：

```text
vision_core:
  可依赖 cuda / tensorrt / opencv
  不可依赖 requests / websocket / grpc

network_client:
  可依赖 https client
  不可依赖 cv2 / PIL / numpy image buffer
```

这样可以从依赖层面证明画面数据无法进入网络模块。

## 18. 风险与应对

### 18.1 DRM/受保护内容黑屏

风险：

部分视频平台会阻止屏幕采集，导致画面黑屏。

应对：

1. 不绕过 DRM。
2. 使用比赛允许的公开视频源或本地播放源。
3. 在文档中说明系统尊重受保护内容限制。

### 18.2 人物漏检

风险：

暗光、遮挡、远景、人群密集时可能漏检。

应对：

1. 调低置信度阈值。
2. 使用更大模型。
3. 输入尺寸从 640 提升到 960。
4. 使用跟踪弥补短暂漏检。

### 18.3 框抖动

风险：

电视剧镜头运动导致框抖动。

应对：

1. 使用 ByteTrack。
2. 对 box 坐标做指数平滑。
3. 镜头切换时清空过旧轨迹。

### 18.4 延迟过高

风险：

模型过大或采集低效导致画框滞后。

应对：

1. 降低输入尺寸。
2. 使用 TensorRT FP16。
3. 只处理最新帧。
4. 限制 FPS 到 30。
5. 只截播放器区域。

### 18.5 隐私质疑

风险：

评委担心系统上传或保存画面。

应对：

1. 展示抓包。
2. 展示输出目录为空。
3. 展示网络 Payload。
4. 展示代码模块隔离。
5. 展示隐私状态面板。

## 23. v1.1 补充：Windows-only 高刷新低延迟路线

本补充基于新的明确约束：

```text
系统平台：只考虑 Windows
屏幕规格：2K 分辨率，最高 300Hz
最低体验：144Hz 以上不出现明显拖框
优先级：稳定高性能 > 功能堆叠
离线能力：不联网时也能获取画面并实时画框
数据策略：不保存、不保留任何画面或检测历史，做到无痕
```

### 23.1 关键结论

最终比赛版不建议使用 Python 作为主程序。Python 可以用于模型验证、导出、离线测试，但最终运行程序建议使用：

```text
C++17/20
DirectX 11/12
DXGI Desktop Duplication 或 Windows Graphics Capture
CUDA
TensorRT
Direct2D/Direct3D/DirectComposition 透明覆盖层
```

原因：

1. 2K + 144Hz/300Hz 场景下，屏幕采集、推理、覆盖层绘制都对延迟敏感。
2. Python 方案容易受 GIL、GUI 事件循环、CPU-GPU 拷贝和解释器调度影响。
3. Windows 原生 DirectX 链路更容易做到稳定、低延迟、少拷贝。
4. TensorRT C++ Runtime 更适合最终打包成 `.exe`。
5. 依赖更可控，比赛环境更容易复现。

### 23.2 不要把“144Hz 支持”误解成“模型必须 144FPS”

电视剧或普通视频源常见帧率是：

```text
24 FPS
25 FPS
30 FPS
50 FPS
60 FPS
```

2K 300Hz 显示器只是刷新率高，并不代表视频内容每秒真的有 300 个不同画面。要做到“不拖框”，核心不是盲目追求模型 300FPS，而是：

1. 采集最新帧，不处理过期帧。
2. 推理结果尽快进入覆盖层。
3. 覆盖层按显示刷新率渲染。
4. 跟踪器根据人物运动做短时预测。
5. 队列不积压，宁可丢帧也不延迟。

推荐目标：

| 子系统 | 推荐目标 |
|---|---:|
| 覆盖层渲染刷新 | 144Hz - 300Hz |
| 屏幕采集 | 120Hz - 240Hz，或按显示器能力取最新帧 |
| 模型推理 | 60FPS - 120FPS |
| 跟踪/预测更新 | 144Hz - 300Hz |
| 端到端延迟 | 优先 < 25ms，最低 < 50ms |
| 队列长度 | 1 - 2 帧 |

如果比赛明确要求“检测输出也必须 144FPS+”，则需要使用更小模型、更低输入尺寸和更强 GPU 优化：

```text
YOLO nano/small
input 512 或 640
TensorRT FP16
GPU 后处理
只检测 person
只截播放器区域
```

### 23.3 最终推荐架构

```text
Windows Display / Player Window
  -> DXGI Desktop Duplication / Windows Graphics Capture
  -> D3D11 Texture
  -> GPU resize + color convert
  -> CUDA / TensorRT inference
  -> GPU/CPU NMS
  -> ByteTrack / Kalman prediction
  -> Screen-space boxes
  -> DirectComposition transparent overlay
```

强烈建议采用“全链路低拷贝”：

```text
屏幕帧尽量保持在 GPU
只把最终少量 box 数据传回 CPU
不要把完整截图从 GPU 拷到 CPU 再拷回 GPU
```

### 23.4 推荐模块替换

原通用文档中提到 Python/OpenCV/Qt 的部分，在最终版中建议调整为：

| 模块 | MVP 可用 | 最终比赛版推荐 |
|---|---|---|
| 屏幕采集 | Python mss/dxcam | DXGI Desktop Duplication / WGC |
| 图像预处理 | OpenCV/Numpy | D3D shader / CUDA kernel / NPP |
| 推理 | PyTorch/ONNX Runtime | TensorRT C++ Runtime |
| 后处理 | Python NMS | TensorRT plugin / CUDA NMS / C++ NMS |
| 跟踪 | Python ByteTrack | C++ ByteTrack / Kalman |
| 覆盖层 | PyQt/PySide | Direct2D/Direct3D/DirectComposition |
| 打包 | Python exe | 原生 C++ exe / installer |
| 日志 | 文本日志 | 严格模式下仅控制台/内存状态 |

## 24. Windows 高性能实现路线

### 24.1 屏幕采集路线

推荐主路线：

```text
DXGI Desktop Duplication API
```

适用：

1. 捕获整个显示器。
2. 适合 2K 高刷新场景。
3. 可以拿到 GPU texture。
4. 延迟低。

备选路线：

```text
Windows Graphics Capture
```

适用：

1. 捕获指定播放器窗口。
2. 用户体验更明确。
3. 可以减少屏幕其他区域干扰。
4. Windows 10/11 现代 API 支持较好。

推荐策略：

```text
比赛模式 A：选择显示器捕获，简单稳定
比赛模式 B：选择播放器窗口捕获，性能更好、误检更少
```

如果只捕获播放器窗口，模型处理区域更小，推理会更稳。但窗口坐标变化、最小化、遮挡和 DPI 映射要处理好。

### 24.2 采集帧率策略

不建议每个显示刷新都强制推理。建议：

```text
capture_rate = 144Hz 或 unlimited latest-frame
inference_rate = 60-120Hz
overlay_rate = display refresh, 144-300Hz
```

实现重点：

1. 采集线程永远覆盖旧帧。
2. 推理线程只拿最新帧。
3. 如果推理忙，直接跳过旧帧。
4. 覆盖层用最新可用 boxes + 跟踪预测绘制。

### 24.3 推理路线

推荐：

```text
ONNX -> TensorRT FP16 engine -> C++ TensorRT Runtime
```

模型建议：

```text
第一版：YOLO small，input 640，FP16
性能不足：YOLO nano，input 512/640
精度不足：YOLO medium，input 640/960
```

输入尺寸选择：

| 输入尺寸 | 优点 | 缺点 |
|---|---|---|
| 512 | 快，适合 144FPS 推理目标 | 远景小人漏检更多 |
| 640 | 性能和精度平衡 | 推荐默认 |
| 960 | 小目标更好 | 推理延迟更高 |

2K 屏幕不代表模型输入也要 2K。通常做法是：

```text
2K capture -> letterbox resize to 640/960 -> inference -> box scale back to screen
```

### 24.4 后处理路线

低延迟目标下，后处理不能成为瓶颈。

推荐优先级：

1. TensorRT engine 内置 NMS 或 EfficientNMS plugin。
2. CUDA NMS。
3. C++ CPU NMS。

MVP 可以用 CPU NMS，但最终版要测延迟。如果单帧人物框数量不多，CPU NMS 也可能够用。

### 24.5 覆盖层路线

最终版不要用慢速 GUI 重绘。推荐：

```text
透明置顶窗口
鼠标穿透
Direct2D / Direct3D 绘制
DirectComposition 合成
```

覆盖层目标：

1. 渲染频率跟随显示刷新，最低 144Hz。
2. 绘制只包含少量矩形线条。
3. 不捕获键鼠。
4. 不改变播放器画面。
5. 不截图、不录屏。

## 25. 防拖框设计

“拖框”通常来自以下问题：

1. 推理处理旧帧。
2. 帧队列过长。
3. CPU-GPU 拷贝太多。
4. 覆盖层刷新慢。
5. 坐标映射延迟。
6. 没有跟踪预测。
7. 播放器窗口移动时坐标没及时更新。

### 25.1 队列策略

必须使用最新帧策略：

```text
FrameSlot latest_frame;

capture_thread:
  latest_frame = current_screen_texture

inference_thread:
  frame = latest_frame
  run inference
```

禁止：

```text
capture -> queue 20 frames -> inference one by one
```

因为这种设计 FPS 看起来高，但画框会永远落后。

### 25.2 三频率解耦

推荐：

```text
采集频率：尽量高，只保留最新帧
推理频率：稳定 60-120FPS
绘制频率：144-300Hz
```

覆盖层每次绘制时：

1. 读取最新 track 状态。
2. 根据当前时间戳预测 box 位置。
3. 绘制预测后的 box。

这样即使推理只有 60FPS，在 144Hz 显示器上也不容易出现框拖尾。

### 25.3 跟踪预测

推荐使用：

```text
ByteTrack + Kalman Filter
```

每个目标维护：

```text
位置
速度
最近更新时间
丢失帧数
置信度
```

绘制时根据时间差预测：

```text
predicted_x = last_x + velocity_x * delta_time
predicted_y = last_y + velocity_y * delta_time
```

注意：

1. 预测时间不要过长。
2. 镜头切换时要快速清空旧框。
3. 人物突然被遮挡时不要长时间残留。

建议参数：

```yaml
tracking:
  max_predict_ms: 80
  max_lost_frames: 4
  position_smoothing: 0.45
  size_smoothing: 0.55
  scene_cut_clear_threshold: 0.65
```

### 25.4 镜头切换处理

电视剧镜头切换频繁，如果跟踪器保留旧框太久，会显得拖框。

可用策略：

1. 如果当前帧检测框与上一帧整体 IoU 很低，认为可能切镜。
2. 如果画面亮度/颜色直方图突变，认为可能切镜。
3. 如果连续目标全部匹配失败，立即清空 track。

注意：直方图只在内存中计算，不保存画面，不记录历史图像。

## 26. 无痕与离线模式设计

### 26.1 离线可运行

系统必须支持：

```text
无网络
本地播放器
本地视频文件
本地模型文件
本地推理
本地画框
```

离线模式流程：

```text
启动程序
检测模型文件是否存在
检测 GPU/TensorRT 是否可用
启动屏幕采集
启动本地推理
启动透明覆盖层
网络线程不启动或进入 offline 状态
```

不联网时仍可运行，因为核心功能不依赖网络。

### 26.2 联网比赛模式

如果比赛要求联网，建议把联网设计成独立控制平面：

```text
online_competition_mode:
  heartbeat: enabled
  visual_upload: disabled
  box_upload: disabled
  frame_hash_upload: disabled
  offline_fallback: enabled
```

断网时：

1. 本地画框继续。
2. 不缓存截图。
3. 不缓存视频。
4. 不缓存检测框坐标等待恢复上传。
5. 只显示网络状态为 offline。

### 26.3 完全无痕的工程定义

“无痕”不是只说“不保存截图”，而是要覆盖这些方面：

```text
不保存原始帧
不保存裁剪图
不保存视频
不保存检测框历史
不保存人物数量历史
不保存 track 历史
不保存窗口标题
不保存 URL
不保存播放器文件名
不保存 OCR
不读取音频
不做人脸 embedding
不上传视觉内容
```

严格模式下建议：

```yaml
privacy:
  zero_retention: true
  save_frames: false
  record_video: false
  save_detections: false
  save_tracks: false
  save_metrics_to_disk: false
  upload_frames: false
  upload_boxes: false
  upload_frame_hash: false
  enable_face_recognition: false
  enable_ocr: false
  enable_audio: false
```

### 26.4 临时缓存限制

允许存在：

```text
TensorRT engine cache
TensorRT timing cache
程序配置文件
模型文件
```

不允许存在：

```text
frame cache
screenshot cache
video cache
detection history
tracking history
visual debug dump
```

### 26.5 调试模式与比赛模式分离

开发阶段可能会想保存 debug 图片来调模型，但比赛要求无痕。建议从工程上分离：

```text
debug build：允许开发者本机调试，可临时保存测试图
competition build：编译期移除保存图像/录屏代码
```

比赛版建议使用编译期宏：

```text
COMPETITION_ZERO_RETENTION=1
```

该宏启用时，相关保存接口直接不可用。
